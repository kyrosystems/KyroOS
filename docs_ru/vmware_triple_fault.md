# VMware: triple fault до входа в ядро

## Подтверждённая причина

Проверено в настоящем VMware Workstation **16.2.4**, BIOS, 4 vCPU,
1024 МБ RAM, IDE HDD 8 ГБ и E1000. Это не эмуляция VMware SVGA в QEMU.

Исходная VM загружала HDD раньше подключённого live ISO. В её MBR есть
сигнатура Limine и указатель Stage 2 по смещению `0x1a4`, равный `512`
(байтовое смещение LBA 1). Однако соответствующие секторы post-MBR gap
заполнены нулями. BIOS передавал управление повреждённой загрузочной цепочке;
VMware фиксировал `vcpu-0 Triple fault`, COM1 оставался пустым.
Замена ISO сама по себе ничего не меняла, поскольку загрузка шла не с него.

Контрольные запуски в отдельной копии VM:

1. Исходные настройки, ISO 1772, HDD подключён: triple fault воспроизводится.
2. Тот же ISO, HDD отключён: загрузка до login успешна.
3. Тот же ISO, HDD подключён, `bios.bootOrder = "cdrom,hdd"`: загрузка успешна.
4. Исходная VM с сохранённым HDD, CD первым, свежий ISO **1774**:
   `SELFTEST_SUMMARY: 10/10`, banner build 1774, `kyroos login:`;
   triple fault в новом VMware-логе отсутствует.

SHA-256 всех трёх сегментов VMDK после проверки совпадает с исходными копиями.
Диск не форматировался и не исправлялся. Изменять ядро для обхода этой причины
не требовалось.

## Безопасное исправление для live-разработки

Выключить VM. Выбрать CD-ROM первым в BIOS boot order и подключить актуальный
ISO при включении. Диск остаётся подключённым и доступным из live-системы.
Для воспроизводимой настройки добавлена утилита:

```powershell
# По умолчанию только проверка/предпросмотр, без записи.
python tools/vmware_live_boot.py "E:\vm\kyroos\KyroOS dev.vmx" `
  --iso KyroOS-26.03.12-1774.iso

# Проверяет через vmrun, что VM не работает, сохраняет байтовую копию VMX,
# затем меняет только boot order и параметры ISO CD-ROM ide1:0.
python tools/vmware_live_boot.py "E:\vm\kyroos\KyroOS dev.vmx" `
  --iso KyroOS-26.03.12-1774.iso --vmrun E:\vmware\vmrun.exe --apply

python tests/test_vmware_live_boot.py
```

Резервная копия: `<имя>.vmx.before-live-boot-<timestamp>.bak`, рядом с VMX.
Исходную копию до любых изменений нужно выбирать по самому раннему timestamp.
Утилита не меняет VMDK, параметры HDD, CPU, RAM, сеть или COM1; отклоняет EFI,
неоднозначные дубли VMX-ключей и попытку использовать слот HDD вместо CD-ROM.
Повторное применение с тем же ISO не создаёт лишних изменений.

## Граница исправления

Это восстановление **загрузки live ISO**, а не ремонт установленной системы.
При извлечении ISO повреждённая HDD-загрузка по-прежнему непригодна.
В диагностической RAW-копии восстановление BIOS stages штатной командой
`limine bios-install` убрало эту раннюю неисправность, но выявило следующую:
`PANIC: fat32: cluster chain read failed (corrupted filesystem?)`.
Поэтому просто записывать Stage 2 в исходный диск недостаточно.
Для самостоятельной HDD-загрузки нужны резервная копия данных и отдельное
восстановление файловой системы/переустановка с разрешения владельца.

Логи воспроизведения и успешных запусков сохранены в
`build/test/vmware-real/` (не включаются в Git):

- `original-vmware.log`, `baseline-vmware.log` — исходный сбой;
- `cd-only-serial.log`, `cd-only-vmware.log` — контроль без HDD;
- `fixed-original-1774-serial.log`, `fixed-original-1774-vmware.log` —
  успешный запуск исходной VM с HDD и ISO 1774;
- `build.log` — сборка ISO 1774.
